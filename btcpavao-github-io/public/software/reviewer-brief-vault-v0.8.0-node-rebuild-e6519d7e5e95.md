## Review procedure and deliverables

1. **Authenticate inputs on your own computer.** With tools obtained independently of the ISO, verify the detached signature on each signed release’s SHA256SUMS and match the specific ISO, source and attachments used. Check the signing key’s full fingerprint separately. Stop if identity or a digest differs. Record filenames, revisions and results. [Signature and file check](https://btcpavao.com/en/bitcoin-core/debian-images/#verify-download).
2. **Establish the upstream baseline.** Authenticate the official Bitcoin Core archive, KeePassXC AppImage and Debian repository metadata against keys you trust. Compare the ISO’s bitcoin-qt, bitcoin-cli and extracted keepassxc program to their counterparts. Validate package versions and contents against Debian’s authenticated archive and identify locally rebuilt packages, launchers and configuration separately. Note libraries and any vendor firmware you accept as inputs. [Bitcoin Core verification](https://bitcoincore.org/en/download/) · [Debian archive authentication](https://manpages.debian.org/trixie/apt/apt-secure.8.en.html) · [KeePassXC verification](https://keepassxc.org/verifying-signatures/) · [Worked comparison](https://btcpavao.com/en/bitcoin-core/debian-images/verification/#upstream-programs).
3. **Account for everything that can affect the wallet.** Inspect the image before booting it. Compare the boot and installer files and extracted filesystem with the authenticated packages, the reviewed build recipe and the project changes. Include file owners, permissions, capabilities, links, library search paths and startup services. Investigate unaccounted-for or unexpectedly modified files, including ones missing from the publisher’s map. The Vault comparison covers 162 installed files and verifies that the two retired session files are absent. The current Node walkthrough illustrates a comparison of chain_backup.py. The earlier 227-file Node check covered the older RC2 ISO. It does not enumerate all possible additions or check their privileges. [Scope and comparison steps](https://btcpavao.com/en/bitcoin-core/debian-images/verification/#compare-source-files).
4. **Test actual behaviour using disposable data.** In a clean VM or on spare hardware, check Vault’s network interfaces, swap, mounts and working files in both live and installed use if both are in scope. With a disposable signing wallet, trace backup, export and restore. Inspect transfer media from a separately trusted system, confirm a watch-only export has private keys disabled and observe what persists after reboot. Compare the intended payment with the recipient, amount and fee before signing. Restore a test backup on a separate offline installation with ordinary GnuPG and Bitcoin Core. Sign a valueless test payment with the recovered wallet. For Node, distinguish persistent watch-only data from temporary work areas. Record the hardware, test conditions and findings. [Two-computer practice](https://btcpavao.com/en/bitcoin-core/self-custody/?setup=vault-node) · [Bitcoin Core offline-signing guide](https://github.com/bitcoin/bitcoin/blob/master/doc/offline-signing-tutorial.md).
5. **Connect reviewed source and resulting bytes.** Inspect the recipe before running it. Build in a clean machine under your control, with no keys or personal files. Hash the result and compare the two complete ISO files. Two project-run [Vault builds](https://github.com/btcpavao/bitcoin-core-vault-releases/actions/runs/44328053285/job/134901484375) matched each other byte for byte and matched the signed Vault hash. Two project-run Node builds also matched the exact Node candidate linked from the main download button. Record the commands, inputs, machine, output hash and comparison result. If it differs, retain both files and logs and leave the source-to-download question open. [Vault build recipe](https://github.com/btcpavao/bitcoin-core-vault-releases/blob/d0bc35aa9a64d45d5c24a226aa9ba2ec2a315ebf/docs/REBUILD.md) · [Node candidate recipe](https://github.com/btcpavao/bitcoin-core-node-releases/blob/e6519d7e5e956aa62512294389a9db2cd0a60a96/docs/REBUILD.md).
6. **Return a signed, dated report.** Name who performed the code review, runtime tests and rebuild, who selected and funded the work, and any relationship with the project. Identify the exact artifact, source and verified upstream inputs. Describe the review scope, observations, reproducible evidence, unexplained differences and limitations in everyday language. Record any fixes and which version was retested. Distinguish the reviewer’s own observations from the publisher’s test results. Explain any remaining questions that matter before the owner uses the release for savings.

Report what each check established. A matching rebuild ties the reviewed inputs to the exact ISO you compared. A code review examines which programs can access the wallet and what they do. A practice payment tests the signing workflow under the conditions you recorded.

The reviewer can complete this work without the owner’s production wallet, passphrases, addresses or holdings. For a later release, identify its exact ISO, review the changes and update the report’s scope before reusing its findings.
